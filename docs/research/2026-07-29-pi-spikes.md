## Spike #1 — Bun-binary parity (RPC + extension loading) — ✅ PASS

Executed on linux-x64 (this exercises the same `bun build --compile` pipeline as the darwin assets; a darwin corroboration run rides the spike-#2 CI workflow).

**Verified:**

- **Checksum verification works as designed.** `SHA256SUMS` is published per release with one line per asset; `sha256sum -c` verified `pi-linux-x64.tar.gz` cleanly. This is the asset `agent_manager.rs` task #15 will verify against.
- **Folder-tarball layout confirmed.** The archive extracts to a `pi/` directory (~122 MB): the `pi` executable plus co-located `photon_rs_bg.wasm`, `theme/`, `assets/`, `node_modules/`, `examples/`, `package.json`. The executable must stay inside this folder — install = extract whole dir, symlink/exec `pi/pi`.
- **The Bun-compiled binary runs without any system runtime.** `--version` → `0.80.6`; no Node/Bun install present was used.
- **`--mode rpc` JSONL framing works.** `{"type":"prompt","message":…}` on stdin produced the full event lifecycle on stdout: `response` → `agent_start` → `turn_start` → `message_start/update(text_delta)/end` → `turn_end` → `agent_end` → `agent_settled`. Exactly the surface the bridge (#7/#8) maps to ACP.
- **TypeScript extensions load in the compiled binary.** A marker extension in `$PI_CODING_AGENT_DIR/extensions/` (type-only import of `ExtensionAPI`, runtime `node:fs`) executed at startup and its `pi.on("tool_call", …)` hook fired during turns.
- **Custom provider + dummy key work.** `models.json` with `{ baseUrl: "http://127.0.0.1:<port>/v1", api: "openai-completions", apiKey: "dummy" }` streamed from a stub OpenAI-compatible server; the stub received `Authorization: Bearer dummy`.

**Findings that correct prior assumptions:**

1. **`PI_CODING_AGENT_DIR` layout is FLAT.** pi writes `auth.json`, reads `models.json`, `extensions/` directly under the dir — there is no `agent/` nesting when redirected (the `agent/` segment belongs to the default `~/.pi/agent` path only). Task #16 must write `models.json`/`settings.json`/`extensions/` at the top of `~/.notesage/agents/pi/`.
2. **pi probes `GET /v1/models` on the configured baseUrl** at session start even with models enumerated in `models.json` (sent without auth header). Harmless for the preset — same localhost origin as the llama-server, which serves `/v1/models` — but the stub in any harness must answer it.
3. Bundled `node_modules` still carries the `@mariozechner` scope alongside `@earendil-works` — cosmetic, but version-pin bumps should re-check extension import specifiers.

## Spike #2 — Zero-network under Seatbelt (PI_OFFLINE=1) — ⏳ authored + proxy question pre-answered; macOS execution pending

Linux sessions cannot execute Seatbelt. **Authored:** `scripts/spikes/pi-seatbelt-spike.sh` (fetch + `SHA256SUMS` verify → flat pi-home → deny-all-network profile with a single `localhost:<port>` allow → three scenarios via `scripts/spikes/pi-seatbelt/rpc-turn.mjs`) and the manually-dispatched workflow `.github/workflows/spike-pi-seatbelt.yml` (`macos-14`, uploads stub log + markers as artifacts). The driver and stub were validated unsandboxed on linux-x64 (turn settles in ~1.6 s).

**Proxy interaction pre-answered on Linux (platform-independent undici behavior):** with `HTTP_PROXY`/`HTTPS_PROXY` pointed at an unreachable address and NO `NO_PROXY` set, pi's localhost provider call still completed — **pi does not honor proxy env vars** for its fetch stack (plain undici ignores them unless explicitly wired). Task #16 keeps `NO_PROXY=localhost,127.0.0.1` as defense-in-depth only, not as a required mitigation. The `NO_PROXY` variant also passed.

**Remaining (macOS only):** the deny-all kernel profile run itself — dispatch the `spike-pi-seatbelt` workflow (or run the script locally) and record the output here. `PI_OFFLINE=1` produced zero non-localhost traffic in every unconfined run so far; the Seatbelt run proves the negative.

## Spike #3 — extension_ui_request permission round-trip — ✅ PASS (with one load-bearing caveat)

Harness: stub server returns a `write` tool call (OpenAI streaming `tool_calls` deltas) on the first completion; a gate extension (`pi.on("tool_call")` → `ctx.ui.select("Allow write?", ["Yes","No"])`) guards it; an RPC driver plays four scenarios.

| Scenario | Result |
| --- | --- |
| **allow** (`extension_ui_response {value:"Yes"}`) | ✅ `tool_execution_start` → UI request → response → tool executes, file written, turn completes |
| **deny** (`{value:"No"}`) | ✅ gate returns `{block:true,reason:"denied by user"}` → `tool_execution_end` with `isError:true` and the reason as the tool result; model continues; file NOT written |
| **abort with the UI request unanswered** | ⚠️ **WEDGES.** After `{"type":"abort"}` pi emitted nothing further — no abort ack, no `agent_end` — for 20+ s until SIGKILL. The blocked `ctx.ui.select` promise is not cancelled by abort. File not written (fail-safe held). |
| **cancel** (`{cancelled:true}`) | ✅ `ctx.ui.select` resolves `undefined` → gate blocks → turn completes normally |
| **cancel-then-abort** | ✅ pending request answered first, then `abort` acks (`response command:abort success:true`) |

**Facts confirmed:** `ctx.hasUI === true` in RPC mode (the gate's interactive path is live, with block-by-default when `hasUI` is false, e.g. `-p` mode). The `extension_ui_request` carries `{id, method:"select", title, options}` — everything the bridge needs to synthesize an ACP `request_permission`.

**Load-bearing rule for bridge task #9:** never lead with `abort` while an `extension_ui_request` is outstanding. The deny/timeout path is: send `extension_ui_response {cancelled:true}` (or `value:"No"`), *then* abort if the turn itself must die. The 30s auto-deny maps to `cancelled:true`.
