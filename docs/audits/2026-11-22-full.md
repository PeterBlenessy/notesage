## Summary

The architecture is sound and most findings from the 2026-07-03 deep review are fixed. The main concern is a recurring pattern: a failed read (iCloud, permissions, a file not yet downloaded) is treated as "empty", shown to the user as the truth, and then written back over the real data. That pattern is behind the library bug fixed in PR #1081 and behind several HIGH findings here (comment sidecars, `project.json`, persisted stores, the library marker). Other notable risks: the AI tool path filter can be bypassed with `..`, agents can write files the unsandboxed app later executes, Copilot chat holds one lock for a whole turn, and three high-severity dependency advisories currently fail the CI audit gate.

### HIGH: Desktop binary cache is never evicted — every PDF/DOCX/EPUB/PPTX opened stays in memory for the whole session
**File:** `src/lib/binary-cache.ts:6` (writers: `src/hooks/useEditorTabContentLoader.ts:57,102`, `src/hooks/useFileOperations.ts:261`, `src/hooks/useAppLifecycle.ts:765`, `src/lib/link-utils.ts:158`, `src/components/sidebar/quiet/FolderPeek.tsx:356`, `src/components/sidebar/quiet/ProjectsSection.tsx:183`)
- `binary-cache.ts` is a module-level `Map<string, Uint8Array>` keyed by absolute path.
- Desktop code calls `setBinaryData` on every binary open, but nothing on desktop ever calls `clearBinaryData`. Its only caller is the mobile `Reader.tsx:1538`.
- `clearAllBinaryData` is never called anywhere, and `editor-store` has no `binary` cleanup on tab close.
- Closing a tab therefore leaves the full file bytes pinned. Opening 20 PDFs of 20 MB each keeps about 400 MB of `Uint8Array`s alive until restart.
- A file that is rewritten and reopened replaces its own entry, but a closed file is never removed.

**Fix:** Call `clearBinaryData(tab.filePath)` from the editor store's close-tab / `markTabDeleted` paths, and on rename (move the key). Alternatively, make the cache an LRU with a byte budget, re-read on miss, and have viewers tolerate a miss by re-fetching through `tauriApi.readBinaryFile`.

### HIGH: PdfViewer never destroys the pdf.js loading task — each mount leaks a dedicated Web Worker plus the parsed document
**File:** `src/components/editor/viewers/PdfViewer.tsx:366-417`
- The load effect calls `pdfjsLib.getDocument({ data: data.slice(), … })`. Its cleanup only sets `cancelled = true`.
- There is no `loadTask.destroy()`, and `pdf.destroy()` is never called on the `PDFDocumentProxy` held in state.
- In the installed pdfjs-dist 6.2.108, `getDocument` with no `worker` option calls `PDFWorker.create({ port: GlobalWorkerOptions.workerPort })`. With `workerPort` unset, the cache lookup misses and **a new `Worker` thread is created for every document** (`node_modules/pdfjs-dist/build/pdf.mjs:15263-15268, 16174-16182`).
- That worker, the parsed document, its page and font caches, and the copied `data.slice()` buffer are only released by `loadingTask.destroy()`.
- So every PDF open, `filePath` change, tab close or viewer remount (view toggles, the mobile Reader) leaks a worker thread and the document's memory.
- Combined with the binary-cache finding above, each PDF opened is retained twice. `mobile-pdf-thumbnail.ts:75` does call `loadingTask.destroy()` correctly, which shows the intended pattern.

**Fix:** In the effect cleanup do `cancelled = true; void loadTask?.destroy();`. Also destroy a superseded document when `pdf` changes, e.g. `useEffect(() => () => { void pdf?.destroy(); }, [pdf])`. Optionally share one `new pdfjsLib.PDFWorker()` across documents.

### HIGH: Stdio MCP servers have stderr piped but never read — chatty servers block once the pipe buffer fills
**File:** `src-tauri/src/commands/mcp/mod.rs:97` (spawn at `:91-117`)
- `start_mcp_server` spawns with `.stderr(Stdio::piped())`, then takes only `stdin` and `stdout`.
- `child.stderr` is never `.take()`n or drained; the `Child` is held in `McpState` for the server's lifetime.
- Once the server writes about 64 KB to stderr, its `write(2)` blocks and the server stops answering JSON-RPC. All its tools then time out and it looks hung.
- Many MCP servers log per request to stderr; the Python SDK, for example, logs "Processing request of type CallToolRequest" at INFO. That limit is reachable in one agent-heavy session.
- The validation path (`:244, :284, read_stderr_tail`) does read stderr, and ACP (`acp/agent_thread.rs` stderr task) and llama-server (`local_inference.rs` `spawn_log_drain`) already drain theirs. MCP is the outlier.

**Fix:** `if let Some(err) = child.stderr.take() { tokio::spawn(drain_lines_to_log_with_bounded_tail(err)); }`, mirroring `spawn_log_drain` and its bounded `log_tail`. Or use `Stdio::null()` if the output is not wanted.

### MEDIUM: Agent-task registry never deletes finished tasks — prompts and outputs accumulate for the app lifetime
**File:** `src/hooks/agent-task/task-registry.ts:35,42` (writer `src/hooks/agent-task/run-task.ts:148`)
- `AgentTaskRegistry.tasks` is a module-singleton `Map<string, InternalTask>`.
- `setTask` is called for every task (`task-${Date.now()}`), but only the test-only `reset()` clears it. Completion, failure and cancel (`useAgentTaskOperations.ts:127-137`) call `runCleanup`, which clears only the `cleanups` map.
- Each record holds the full `prompt` and the full streamed `output`.
- Comment delegations, inline tasks and especially scheduled or file-triggered automations (`useAutomationRunner`) create tasks continuously, so memory grows without bound in a long-running (tray-resident) app.

**Fix:** Delete the task record a short time after a terminal transition, e.g. in `complete` / `fail` / `cancelTask` call `setTimeout(() => agentTaskRegistry.deleteTask(id), 60_000)`. Or cap the map (LRU of the last N tasks), since the UI mirror lives in `activity-store`.

### MEDIUM: Completion llama-server buffers its entire session's stdout/stderr in memory via `wait_with_output`
**File:** `src-tauri/src/commands/local_inference.rs:932-944`
- `start_completion_server` spawns with piped stdout/stderr, then `tokio::spawn(async move { child.wait_with_output().await … })`.
- `wait_with_output` reads both streams into `Vec<u8>` until the process exits.
- llama-server writes per-request timings to stderr, and FIM requests fire on every debounced keystroke. Memory therefore grows for the whole session and is only logged (then dropped) at exit.
- This is the exact problem the main server fixed. The comment at `:47-52` says "accumulated the entire session's output in memory, on a machine already spending most of its RAM on model weights", and the main server now uses `spawn_log_drain` + `LOG_TAIL_CAPACITY = 400`.

**Fix:** Take stdout/stderr and feed them to the same `spawn_log_drain`, or to a separate bounded tail, then `child.wait()` for the exit status.

### MEDIUM: Agent/server kills signal only the direct PID — grandchild processes are orphaned
**File:** `src-tauri/src/commands/acp/agent_thread.rs:597-623`, `src-tauri/src/commands/acp/state.rs:52-54`, `src-tauri/src/commands/process_guard.rs:68-80`
- No spawn site puts the child in its own process group: there is no `process_group(0)`, `setsid` or `pre_exec`. All kills (`libc::kill(pid, SIGKILL)` in `stop_all_sync`, `terminate_with_escalation`, `kill_on_drop`) target one PID.
- ACP agents routinely spawn subprocesses: the Claude Code / Codex shell and tool commands, their own MCP servers, and npm agents launched as `node …` children.
- SIGKILLing the agent gives it no chance to reap them. Long-running children (dev servers, watchers, MCP servers) survive app quit, agent restart and workspace switch (`stopAllAcpAgents`).
- The startup orphan sweep only knows the recorded top-level PID.

**Fix:** Spawn with `cmd.process_group(0)` (tokio `Command::process_group`, Unix) and signal the group with `libc::kill(-pgid, SIG…)`. Apply the same to MCP stdio servers and llama-server. On Linux, `bwrap --die-with-parent` additionally helps the sandboxed path.

### MEDIUM: Calibration llama-server's stdout/stderr are piped but never drained
**File:** `src-tauri/src/commands/model_fit/calibration.rs:74-75`
- The calibration server is spawned with `.stdout(Stdio::piped()).stderr(Stdio::piped())`, but neither stream is ever taken or read. The only `stdout` use, at `:36`, belongs to the separate `ps` call.
- llama.cpp prints a lot at model load (metadata, tensor/Metal init) and per request. If that exceeds the pipe buffer, the server blocks on write.
- The `/health` poll then fails after about 60 s, or the timed requests stall, so calibration fails or reports skewed timings depending on model log volume.
- Severity rests on that log-volume dependency; I did not reproduce the stall.

**Fix:** Use `Stdio::null()` (calibration does not use the output), or drain both streams with `spawn_log_drain`.

### LOW: `useAutomationRunner` / `MissedRunsDialog` — un-guarded `.then(u => unlisten = u)` listeners
**File:** `src/hooks/useAutomationRunner.ts:214-283`, `src/components/automations/MissedRunsDialog.tsx:29-45`
- Both register their listeners with the textbook broken shape: `useAutomationRunner` has three (`automation-due`, `file-changed-batch`, `file-renamed`) and `MissedRunsDialog` has one (`automations-missed`), with no `mounted` flag.
- Both mount at App root with `[]` deps, so production is unaffected. But `main.tsx:138` uses `<React.StrictMode>`, whose dev mount → cleanup → mount runs before the promises resolve.
- The first set of listeners therefore leaks for the session. In dev every automation event dispatches twice (mitigated by the single-mode manager and the debounce), and the missed-runs notification fires twice.

**Fix:** Apply the `useSandboxViolations` shape: `let mounted = true; … .then(fn => mounted ? (u = fn) : fn())`, with `mounted = false` first in cleanup.

### LOW: inline-diff — module-global `activeWidgets` keeps document capture listeners and destroyed editors alive, and is shared across editors
**File:** `src/components/editor/extensions/inline-diff.ts:10, 170-175, 279-283, 305-314`
- Each hunk widget adds `document.addEventListener('click', dismiss, true)` and registers its teardown in a module-level `Map<HTMLElement, () => void>`.
- Teardown happens only in `clearInlineDiff` or on the next `buildDiffDecorations` (for disconnected nodes).
- If the editor is destroyed (tab close) while an external-change diff (`useFileWatcherIntegration.ts:134,210`) is showing, the capture listeners and their closures, which hold `editor`, stay alive until a diff is next built anywhere.
- Because the map is global, `clearInlineDiff(editorA)` also tears down editor B's widget listeners in split view.

**Fix:** Key the map per editor (a `WeakMap<Editor, Map<…>>`) and add a plugin `view().destroy` that runs that editor's cleanups. Or use a single delegated document listener per plugin view.

### LOW: Desktop thumbnail cache keeps superseded blob URLs (`path@modified` keys) and is unbounded
**File:** `src/lib/desktop-thumbnails.ts:32, 63-70`
- The key includes `modified`, so a file rewritten in place gets a new entry while the old `blob:` URL (HTML lead image) stays pinned.
- `evictDesktopThumbnail` only runs on inbox move/trash (`inbox-store.ts:462,516`).
- `mobile-thumbnails.ts:388-405` documents this exact leak and fixes it with `releaseEntry`; the desktop twin does not.

**Fix:** In `getDesktopThumbnail`, evict and revoke any other key with the same `path@` prefix before inserting. Optionally add an LRU cap.

### LOW: Timers not cleared on unmount
**File:**
- `src/components/actions/ActionsDashboard.tsx:44`: `spinTimer` → `setSpinning` after unmount.
- `src/components/settings/AddCustomModelDialog.tsx:324`: `searchTimerRef` has no unmount cleanup, so closing the dialog within 400 ms still fires a Hugging Face search (network) and sets state on the unmounted dialog.
- `src/components/chat/ToolCallPermissionCard.tsx:46,64`: the 1.5 s `onResolved` timeouts are untracked.

**Fix:** Add `useEffect(() => () => clearTimeout(ref.current), [])` for each, and track the ToolCallPermissionCard timeouts in a ref.

### LOW: `useLocalCompletion` AbortController is aborted but never consumed (false cancellation)
**File:** `src/hooks/useLocalCompletion.ts:145-149, 176, 253-256`
- The controller is created and `.abort()`ed on supersede and unmount, but it is never passed into `ollamaFimCompletion` / `localBundledFimCompletion` / `openaiCompatibleFimCompletion`; Tauri `invoke` takes no signal.
- Superseded FIM requests keep running on llama-server or Ollama. Only `signal.aborted` / `requestId` act as discard guards. This is the case the skill names explicitly, and it is still present.

**Fix:** Drop the controller and keep the `requestId` guard, or add a backend `cancel_fim(requestId)` command.

### LOW: Event-driven promises with no timeout leave listeners registered forever if the terminal event never arrives
**File:** `src/hooks/useCopilotChat.ts:130-192` (`generateText`), `src/lib/ai/structured.ts:84-133`
- `generateText` resolves only on `copilot-chat-done`. If the LSP crashes or never emits done after `conversation/create` resolves, the chunk/done listeners and the pending promise live for the session.
- `generateStructured` awaits `done` after `invoke` resolves. If `ai-stream-done` is never emitted (backend error path), the same happens.
- The `structured.ts` half was flagged in the prior audit (async section) and is still present.

**Fix:** Race the event promise against a timeout, or against the invoke settling plus a grace period. Always unlisten in `finally`.

### LOW: Background-task strategies can leak listeners registered before `registerCleanup`
**File:** `src/hooks/agent-task/acp.ts:137, 228, 270`, `src/hooks/agent-task/copilot-lsp.ts:50-181`
- ACP: `await listen('acp-session-update')`, then `await getHomeDir()` (a `tauriApi` call that can reject), then the second listen, then `registerCleanup`. A rejection in between leaks the first listener, which filters on instance/session ids and so fans out harmlessly.
- Copilot: eight sequential `await listen()` calls run before `registerCleanup`; a mid-sequence failure leaks the earlier ones.
- A Copilot task whose `copilot-chat-done` never arrives keeps all eight until the user cancels.

**Fix:** Register via `Promise.all` with a try/catch that unwinds whatever resolved, and call `registerCleanup` immediately with a closure over a mutable array. Add an inactivity timeout for Copilot tasks.

### LOW: `image-compress` leaks the blob URL when the image fails to load
**File:** `src/lib/image-compress.ts:20, 28, 115-117`
`URL.revokeObjectURL` runs only on the success path after drawing. `img.onerror` rejects without revoking.
**Fix:** Revoke in `onerror` too (or in a `finally` around the load).

### LOW: markdown-worker — abort listener not `{ once: true }`; a worker crash leaves a dead singleton
**File:** `src/lib/markdown-worker.ts:103-110, 154`
- The `signal.addEventListener('abort', …)` is never removed after the parse resolves. It is minor because signals are per-activation.
- More importantly, the worker `error` handler rejects pending parses but does not reset `workerInstance` / `workerReady`. After a module-load error, `preReadyQueue` keeps growing and every later parse hangs.

**Fix:** Use `{ once: true }`, and remove the listener on settle. In the `error` handler, terminate the worker and null `workerInstance`, reset `workerReady`, and reject and clear `preReadyQueue`.

### LOW: `startInboxProgressSync` returns the raw store unsubscribe on re-entry
**File:** `src/lib/inbox-progress-sync.ts:189`
- `if (unsubscribe) return unsubscribe;` hands a second caller the raw Zustand unsubscribe rather than the wrapper.
- If that caller cleans up, the subscription is removed but the module `unsubscribe` is never nulled, so a later `startInboxProgressSync()` returns a dead handle and never re-subscribes.
- Today there is only one caller (`MobileApp.tsx:69`), so this is latent.

**Fix:** Keep the wrapper in a module variable and return that, or use ref-counting.

### LOW: Copilot LSP not stopped on `RunEvent::Exit`; exit-time `try_lock` can skip all teardown
**File:** `src-tauri/src/lib.rs:629-640`, `src-tauri/src/commands/copilot_lsp.rs:298`, `src-tauri/src/commands/acp/state.rs:38-44`, `src-tauri/src/commands/mcp/state.rs:61-67`
- The Exit handler stops ACP, the network proxy, MCP, llama-server and the sandbox monitor, but not `CopilotLspState`.
- Tauri exits through `std::process::exit`, so `kill_on_drop` never fires. The LSP has no PID file and no startup orphan sweep; shutdown relies on the server noticing stdin EOF.
- `AcpState::stop_all_sync` and `McpState::stop_all_sync` use `try_lock()` and return early (killing nothing) if any task holds the lock at quit, e.g. during a spawn.

**Fix:** Add a `CopilotLspState::stop_sync` (kill by stored PID) to the Exit handler. On `try_lock` failure, fall back to PID-based kills (ACP already records `child_pid` atomics and PID files).

### LOW: `run_in_terminal` spawns `osascript` without waiting (zombie per call)
**File:** `src-tauri/src/commands/dialog.rs:92-95`
The `std::process::Child` is dropped without `wait()`, so each call leaves a zombie until the app exits. Calls are rare (auth flows).
**Fix:** Use `.status()` / `.output()` on a blocking task, or spawn a thread that `wait()`s.

### LOW (consistency, still present from prior audit): `return () => promise.then(fn => fn())` unlisten shape
**File:** `src/components/settings/ConnectCopilotLsp.tsx:103-107`, `src/hooks/useNetworkDomainApprovals.ts:103-106`, `src/hooks/useInboxArrivals.ts:110-113`, `src/components/editor/DrawingPreview.tsx:177`, `src/hooks/useDocumentRelations.ts:122-125`, `src/hooks/useFileRenameSync.ts`, `src/hooks/useFileWatcher.ts:247-261`
- These are not leaks: each cleanup always unlistens. The residual risk is the brief post-unmount window; handlers self-guard via `getState()`.
- `ConnectCopilotLsp` also re-subscribes three listeners per `retryCount` / `completeAuth` change, and `console.log`s every `copilot-lsp-message` payload (`:99`). Devtools retains those objects.
- `useDocumentRelations` re-subscribes when `refresh` identity changes, which can drop a `links-reindexed` event mid-swap.
- `DrawingPreview` re-subscribes on `[drawingJson, drawingId]`.

**Fix:** Standardise on the `mounted`-flag + immediate-unlisten form. Remove the debug `console.log`. Read `refresh` through a ref so the listener can be app-lifetime.

## 2. Async Flows & Race Conditions

HIGH 3, MEDIUM 14, LOW 7

The 3 HIGH findings are all new: tab content can be overwritten by another tab's text, model-fit calibration never records, and Copilot chats leak into each other. Of the 9 async findings in the 2026-07-03 audit, 7 are fixed (all 3 instant-load HIGHs, the ACP sessionId gate, the direct-API tool-call cancel, and the Copilot supersede guard and getState-in-deps issue in the Tiptap hooks). One is partly fixed: the CodeMirror Copilot hook still has both gaps. One LOW is unchanged (`generateStructured`). I ran every step in SKILL.md. Every finding below comes from reading the code path; none are flagged on a pattern name alone.

### HIGH: Module-level `serializeTimer` is not flushed or cancelled on tab switch, so tab A can be overwritten with tab B's content
**File:** `src/hooks/useEditor.ts:51` (timer at `:304-309`), `src/components/editor/Editor.tsx:139-152`
`serializeTimer` lives at module scope. The 150 ms debounced callback captures `editor` and the `onUpdate` from the render in which the key was pressed. That `onUpdate` is `handleUpdate`, which closes over `activeTab = A`. Tiptap 3 refreshes the options on every render, but the callback already queued keeps the old closure.
- If the user types in A and switches tabs within 150 ms, `useEditorTabSwitch` loads B into the same editor. All of its load paths (`editor.view.updateState(cachedState)`, `loadRawMarkdownIntoEditor`, `streamingHydrate`) either dispatch no transaction or tag it `addToHistory:false`, so the pending timer is never cleared.
- The timer then fires and runs `getMarkdownFromEditor(editor)`, which returns **B's** markdown, then calls `handleUpdate_A(...)` → `updateTabContent(A.id, B_markdown, true)`.
- A is marked dirty with B's body and autosave/Cmd+S writes it to A's file. Typing and then Ctrl+Tab / Cmd+click is enough to trigger this.
- The timer is also never cleared on unmount, so it can serialize a destroyed editor.
- New; not in the prior audit.
**Fix:** Move the timer into a ref inside `useEditor`. Capture the tab id or file path when the timer is scheduled and pass it to `onUpdate`, or drop the update if the editor's loaded tab has changed. Flush the pending serialize synchronously at the top of the tab-switch effect, before `cachedEditorStatesRef.current.set(prevFilePath, …)`, and clear it on unmount.

### HIGH: `useModelFitCapture` listens on global stream event names that are never emitted, so runtime calibration never records
**File:** `src/hooks/useModelFitCapture.ts:59-92`; emitter `src-tauri/src/commands/local_inference.rs:1464`
- The hook subscribes to plain `ai-stream-chunk`, `ai-stream-thinking-chunk` and `ai-stream-done`.
- Since the streamId change, every `ai_chat_stream` caller passes a `streamId` (`useDirectApiChat.ts:566/761`, `agent-task/direct-api.ts:85`, `structured.ts:128`). The backend therefore emits only `<name>:<streamId>` (`ai_streaming.rs:16`). Tauri does no wildcard matching, so `onChunk` and the done handler never fire and `recordMeasurement` is unreachable.
- `ai-stream-timings` is still emitted globally with no streamId. If the capture is re-wired, overlapping local generations would also take each other's timings.
- New; it comes from the correlation change.
**Fix:** Emit `ai-stream-timings` through `stream_event(…, stream_id)` with the streamId in the payload. Then either have the chat and task paths call a capture API with their streamId, or have the backend emit one global "generation finished" event carrying `{streamId, tokPerSec, tokens}`. Capture should key on streamId.

### HIGH: Copilot chat keeps one `conversationIdRef` / `cleanupRef` per hook for all Notesage conversations
**File:** `src/hooks/useCopilotChat.ts:78-79, 331-335, 783-798, 840-851`; `src/hooks/useAIOperations.ts:233-234`
- The Copilot LSP conversation id lives in a single ref on the always-mounted `FloatingCommandBar` instance. Nothing resets it when `activeConversationId` changes.
- After chatting in A and switching to B (new or existing), B's message goes out as `copilotLspConversationTurn(A's copilot id, …)`. B's answer sees A's history, which can cross projects; this is the leak `buildAcpHistoryBlock`'s #468 comment warns about.
- The single `cleanupRef` means a send in B tears down A's still-streaming listeners. A's message gets finalized while the LSP keeps generating.
- `useAIOperations.cancelChat` always calls `cancelCopilotChat()`, so pressing Stop on any provider's chat destroys whichever Copilot conversation the ref holds.
- Direct-API and ACP were moved to per-conversation maps (`streamsRef`, `cleanupRefs`); Copilot was not. New.
**Fix:** Key both the Copilot conversation id and the cleanup by Notesage `conversationId` (a Map, as in `useDirectApiChat.streamsRef`). Persist the Copilot id per conversation or reset it on conversation switch. Only call `cancelCopilotChat(convId)` when the target conversation's run path is `copilot_lsp`.

### MEDIUM: ACP `retryWithRestore` reads the active conversation instead of the failed one, and `lastPromptRef` is one slot shared by concurrent conversations
**File:** `src/hooks/useAcpLifecycle.ts:406-418, 565-575, 906, 930`
- The send path passes `conversationId` to `resolveActiveSessionId(…, conversationId)` and `buildAcpHistoryBlock(…, undefined, conversationId)`. The retry path does not: `resolveActiveSessionId(liveAgent.chatSessionId)` at :906 and `buildAcpHistoryBlock([…])` at :930.
- When a background or cap-deferred conversation hits a connection error and auto-retries (:712), the replayed history is from the chat the user is *viewing*. That is a cross-conversation, possibly cross-project, leak. The prompt may also target another conversation's branch session id.
- Separately, `lastPromptRef` is overwritten by every send. If A and B are both in flight and A hits a connection error, `retryWithRestore()` replays **B's** prompt into B. A's message is then never errored and its run stays `running`.
- New.
**Fix:** Pass `prompt.conversationId` to both helpers. Make `lastPromptRef` a `Map<convKey, PromptCtx>` and have `retryWithRestore(convId)` take the conversation explicitly; the banner passes the foreground id.

### MEDIUM: ACP Stop during agent cold-spawn or session creation is ignored, and the prompt is still sent and streamed
**File:** `src/hooks/useAcpLifecycle.ts:577-692` vs `acpCancelChat` `:973-1064`
- `acpCancelChat` can only cancel when `agent?.chatSessionId && agent?.instanceId` (:989) and a cleanup is registered.
- During `await ensureAcpAgent` (:580, seconds on a cold spawn), `startFreshChatSession` (:619) or `attachTurnListeners` (:637), it just calls `runIdle` and `setLoading(false)`.
- `acpSendChatMessage` has no cancelled check after those awaits. It attaches listeners, calls `acp_session_prompt`, and the reply streams into a message the user stopped. Run state has already been cleared, so the orb and history show it idle while it streams.
- New (SKILL "cancel during the listener-registration window").
**Fix:** Keep a per-send cancel token (a `Map<convKey, {cancelled:boolean}>`) and set it in `acpCancelChat` before anything else. Check it after every await in send and retry; on cancel, bail and run the conversation's cleanup.

### MEDIUM: Direct-API Stop during compaction or listener registration does not stop the backend stream
**File:** `src/hooks/useDirectApiChat.ts:583-710, 747-749`; `src-tauri/src/commands/ai.rs:41-50`
- **Compaction window:** for `local_bundled`, `await compactForProvider(...)` (:747) runs a full `ai_chat` generation after `streamsRef.set`. A Stop there calls `ai_chat_stream_cancel(streamId)`, but the stream is not registered yet, so `AiStreamState::cancel` returns false and nothing is stored. `cleanup()` sets `cancelled`, but :749 still calls `invoke('ai_chat_stream')` with no check. The local model then generates the whole reply into torn-down listeners, holding the single bundled server.
- **Listener-registration window:** `streamsRef.set` only happens after `await Promise.all([listen…])` (:583-710). A Stop during that window finds no handle and the turn proceeds, while `runIdle` is never called.
- The prior LOW called this ordering "safe today"; it is only safe for the backend half.
**Fix:** Add `if (cancelled) return;` after `compactForProvider` and before the first invoke. Register a provisional handle (a cancel flag) before awaiting the listeners. Optionally make the backend keep a short-lived "cancelled before register" tombstone keyed by streamId.

### MEDIUM: A failing tool continuation in `useDirectApiChat` never calls `cleanup()`
**File:** `src/hooks/useDirectApiChat.ts:647-661`
- If the continuation `invoke('ai_chat_stream')` (:554) rejects (429, network, context overflow) or a tool throws, the `.catch` sets the error, loading and run state but does not call `cleanup()`.
- The 8 listeners and the 50 ms `flushInterval` stay alive until the next send in that conversation. Running/thinking segments are never finalized and the `streamsRef` entry stays stale.
- The outer `catch` (:767) does call cleanup, so the two paths behave differently. New.
**Fix:** Call `cleanup()` in that `.catch`, then set the error and `runError`; the order matters because cleanup calls `runIdle`.

### MEDIUM: Copilot chat tool-call and permission paths do not handle cancellation
**File:** `src/hooks/useCopilotChat.ts:224-234, 292-320, 563-595, 730-750`
- `cleanup()` does not resolve the pending tool-permission promise. A Stop while the card is up leaves the card live. A later click runs `executeToolCall` and sends a result into a finalized turn or destroyed conversation.
- `handleToolCall` never checks `cancelled` after awaiting the permission or `executeToolCall`, so it pushes segments into an already-finalized message.
- `decision$` in the confirmation handler has no rejection or cancel path.
- This is the sibling of the direct-API finding that has been fixed; the Copilot path was not updated.
**Fix:** Mirror `useDirectApiChat` cleanup at :687-691. Pass a cancelled getter into `handleToolCall` and bail after each await.

### MEDIUM: Copilot event correlation latches onto the first `conversationId` it sees, and an empty id is accepted by every listener
**File:** `src/hooks/useCopilotChat.ts:138-145, 434-442`; `src/hooks/agent-task/copilot-lsp.ts:40-47`; `src-tauri/src/commands/copilot_protocol.rs:315-353`
- `generateText`, a first-turn chat create, and Copilot agent tasks all listen on the same global `copilot-*` names and latch onto whatever conversationId arrives first.
- A `generateText` (Improve/Summarize from the BubbleMenu) started while a chat or task stream is mid-flight latches onto that stream's chunks and resolves with its text. Two creates started close together can swap streams.
- The backend sends `conversationId: ""` when the LSP omits it, and `!payload.conversationId` returns true in every listener. One `copilot-tool-confirmation` can then show a card in chat *and* be auto-approved by an agent task for the same `requestId`.
**Fix:** Add a client-generated correlation id to the create call, for example a `workDoneToken` the backend echoes into each emitted payload, and filter on it. Treat a missing id as "not ours".

### MEDIUM: Background agent-task cancel only acts in the frontend for direct-API and Copilot tasks
**File:** `src/hooks/useAgentTaskOperations.ts:106-140`; `src/hooks/agent-task/direct-api.ts:51-94`; `src/hooks/agent-task/copilot-lsp.ts:170-190`
- `cancelTask` only cancels backend-side when `task.instanceId && task.sessionId` (ACP).
- Direct-API tasks never store their `streamId` and never call `ai_chat_stream_cancel`, so the provider stream runs and bills to completion after "Cancel".
- Copilot tasks never destroy their LSP conversation.
- `cancelTask` returns `false` for these tasks, so `useCommentDelegation` shows "agent had already finished", which is wrong.
- The invoke `.catch` → `handle.fail` does not check `status === 'cancelled'`, so a late network error toasts "Agent failed" after the user cancelled.
- This is the SKILL's "frontend-only cancel of a backend-driven stream" pattern, still present in agent tasks.
**Fix:** Store the `streamId` (or Copilot conversation id) on the `InternalTask` and call the matching cancel or destroy in `cancelTask`. Return true. Have `fail` and `complete` early-return when the status is `cancelled`.

### MEDIUM: Comment-delegation cancel during the spawn window does nothing, and the task later overwrites the cancel
**File:** `src/hooks/useCommentDelegation.ts:90-196, 401-433`
- `taskId` is only stored on the comment after `await startTask(...)` resolves (:195), and the ACP spawn takes seconds.
- A Cancel in that window finds no `comment.taskId` and logs "Cancelled — no active task". It sets the status back to open, but the task keeps running.
- `onComplete` later adds the agent reply and sets the status to `done`, undoing the cancel.
- `cancelDelegation` also reads `comment.taskId` from the passed-in object, which may be a stale render snapshot, rather than the store.
**Fix:** Record a per-comment "cancel requested" flag in the store. Check it in `onComplete`/`onError`/`onChunk`, and right after `startTask` resolves; if set, call `cancelTask(taskId)` immediately. Read `taskId` from the store.

### MEDIUM: Eager ACP session writes are not gated on `active` and can target the wrong conversation
**File:** `src/hooks/acp/useEagerAcpSession.ts:82, 120-150`
- The `active` flag is only checked before storing the listener. After a conversation switch mid-flight, the IIFE still runs `restoreOrCreateAcpSession`, sets `boundAgent.chatSessionId` and calls `useChatStore.getState().setSegmentSessionId(session.session_id)` (:149).
- That call passes no `convId`, so it writes to whatever conversation is active *now*. The send path passes `convId` here.
- `convId` (:120) and the `conv` read after the `ensureAcpAgent` await (:126-128) can refer to different conversations. The agent keyed to `convId` can then be restored onto another chat's `storedSessionId`.
- The module lock `if (eagerSessionPromise) return` (:82) silently drops the switched-to conversation's restore. Nothing re-runs it when the lock clears.
- This extends the prior "eager-session listener race" (that part is fixed).
**Fix:** Check `active` after every await. Use one captured `convId` throughout and pass it to `setSegmentSessionId`. When the lock is held, chain a re-check after it settles instead of returning.

### MEDIUM: Four `useAcpLifecycle` instances compete for the singleton `acpUnresponsiveMonitor`
**File:** `src/hooks/useAcpLifecycle.ts:360-369, 1068-1069`; instances via `useAIOperations()` in `BubbleMenu.tsx:43`, `SourceBubbleMenu.tsx:24`, `FloatingCommandBar.tsx:137`, `useCommentEditorSync.ts:19`
- The monitor's header assumes one owner. In practice every instance calls `setOnUnresponsive` on mount and `setOnUnresponsive(null)` on unmount.
- `BubbleMenu` mounts and unmounts with `showFloatingToolbar`, view mode and tabs. Its unmount clears the callback, and `start()` then returns early, so hung-agent detection is silently disabled for the command bar's sends.
- `setRetryCallback(retryWithRestore)` runs during *render*, so the last instance to render wins. A selection-driven BubbleMenu render installs a retry whose `lastPromptRef` is null, and the banner's Retry button does nothing.
- An instance's `checkAgentAndNotify` also cleans its own empty `cleanupRefs`, not the stuck conversation's.
**Fix:** Have only the chat-owning instance (`FloatingCommandBar`) register monitor callbacks, for example via an `ownsChatLifecycle` flag. Move the registration into an effect with a compare-and-clear on unmount (`if (monitor.cb === mine) set(null)`).

### MEDIUM: `useCopilotCompletionCM` still has the stale-completion and non-reactive-dependency bugs fixed in the Tiptap hook
**File:** `src/hooks/useCopilotCompletionCM.ts:94-136, 158, 199-203`
- It has no monotonic `requestId` and no requested-anchor check. After the await it only checks `cmView.hasFocus` and paints at the *current* `selection.main.head` (:120), so a slow response N lands at the caret after N+1.
- `useSettingsStore.getState().inlineCompletionsDisabled` is in the dependency arrays at :135 and :203, so toggling the setting does not re-arm the effects.
- `useCopilotCompletion.ts` (:278-292) and `useLocalCompletion.ts` are fixed. Prior MEDIUM: partly fixed, still present in the CodeMirror sibling.
**Fix:** Copy the Tiptap hook's guard (`thisRequest = ++requestId.current`, compare after the await, discard if `head !== requestedPos`). Subscribe with `useSettingsStore((s) => s.inlineCompletionsDisabled)`.

### MEDIUM: Pending-comment files from agents are processed without per-path dedup, so comments can be added twice
**File:** `src/hooks/useFileWatcher.ts:204-213`; `src/lib/pending-comments.ts:116-117, 164-172, 236-246`
- Each create/modify event schedules its own 300 ms `setTimeout(processPendingCommentFile)`. Unlike `modifyDebounce`, there is no per-path debounce and no in-flight set.
- An agent's create followed by a modify in different batches starts two concurrent runs. Both read `status !== 'processed'` (the status is written only at the end, after several awaits) and both add every comment.
- `isActiveFile` and `editor` are captured before `await loadComments`. If the user switches tabs during that await, `findTextInDoc` runs on the wrong document and `setCommentDecorations` puts this file's comments on another document's editor.
**Fix:** Debounce per path through a `Map<path, timer>` and keep an in-flight `Set<path>`. Re-read the active tab and editor after the awaits.

### MEDIUM: `PptxViewer` parse has no staleness guard and the viewer is not keyed by file
**File:** `src/components/editor/viewers/PptxViewer.tsx:100-129`; `src/components/editor/EditorViewerContainer.tsx:84`
- The same `PptxViewer` instance is reused across `.pptx` tabs because there is no `key`.

- Results also land after unmount.
**Fix:** Add `let cancelled = false; return () => { cancelled = true }` and check it in both `.then` and `.catch`. Alternatively render with `key={activeTab.filePath}`.

### MEDIUM: Automation guardrails are recorded when a run executes, not when it is admitted, so queued bursts bypass debounce and the daily cap
**File:** `src/hooks/useAutomationRunner.ts:176-203`; `src/lib/automations/executor.ts:149-180`

**Fix:** Call `record()` at admission, when `request()` returns `started` or `queued`. Include queued jobs for the key in the cap count.

### LOW: `generateStructured` has no timeout or error event, and no production callers

### LOW: CodeEditor language load and ChartNodeView migration write have async races

### Confirmed Good Patterns
**Prior-audit items, now fixed (checked in code):**
- `previewInFlightRef` is cleared at the abort site (`useEditorTabSwitch.ts:173`).
- The unmount cleanup aborts the pipeline and clears the dedup ref (`:744-749`).
- `streamingHydrate` checks `signal.aborted || editor.isDestroyed` before and after every yield, before `updateState`, and inside the deferred annotation rAF (`markdown.ts:305-391`). `markdown-worker.ts:149` honours the signal.
- `useCopilotCompletion` has a `requestId` supersede guard and a requested-anchor check (`:274-292`). It and `useLocalCompletion` subscribe to `inlineCompletionsDisabled` with a selector.

- The direct-API tool loop checks `cancelled` after the permission await, after the tool await and before the continuation. `cleanup` resolves the pending permission with `'deny'` (`useDirectApiChat.ts:414, 503, 551, 687-691`).

**Event bus:** I enumerated every `.emit(` in `src-tauri/src` (34 distinct names).
- AI stream events are suffixed by streamId and all four `ai_chat_stream` callers pass one.
- `transcription-progress` is correlated by job id; `local-model-download-progress` and `model-download-progress` carry a `model` key.
- `agent-install-progress` carries `agentId`; ACP events carry instanceId and sessionId.

**Backend cancel:** `AiStreamState` uses `notify_one` + `tokio::select!` and closes the register→await race (only a cancel issued before registration is lost, MEDIUM above).

**Concurrency and dedup:**
- ACP spawn uses an in-flight promise map.
- `processSendQueue` has a re-entrancy guard; each send path calls `runStarted` synchronously before its first await, so the cap check stays accurate.
- `RunManager` serializes runs, and `restart` aborts through an AbortController that is consumed.
- `useMessageQueueDrain` is FIFO, one per idle transition, and dispatches through a ref.

### MEDIUM: Stream chunks are written to the chat store unbatched, defeating the 50 ms flush and re-parsing the growing markdown on every token
**File:** `src/hooks/useDirectApiChat.ts:584-589` (ACP path: `src/hooks/useAcpSessionListeners.ts:158-160`)

### MEDIUM: Comment decoration sync fires an extra transaction and a full decoration rebuild on every keystroke in commented documents
**File:** `src/hooks/useCommentOperations.ts:140` and `:166-188`

1. The `transaction` listener calls `updateCommentPositions` on every `docChanged` transaction. That is every keystroke while a comment's anchor shifts or its text is edited.

### MEDIUM: Thinking-tag stream parser duplicated in two modules; the `ai_streaming.rs` copy byte-slices a `String` at a position that may fall mid-character (possible panic)
**File:** `src-tauri/src/commands/ai_streaming.rs:876`
`ollama_chat_stream` (ai_streaming.rs 856–912) and `local_bundled_chat_stream` (local_inference.rs 1347–1426) each contain their own streaming `<think>`-tag scanner. They have drifted apart:
- The local_inference copy holds back from `rfind('<')`, which is always a safe character boundary.
- The ai_streaming copy computes `let safe = tag_scan_buf.len() - hold` (with `hold = tag.len() - 1`) and then does `&tag_scan_buf[..safe]` (lines 876/878 and 900/902). That is a byte offset, not a character boundary.

**Fix:** Extract one tested `ThinkingTagScanner` (feed a chunk, get thinking/text pieces back) into `thinking_tags.rs` or `segment_builder.rs` and use it from both streams. Hold back with `floor_char_boundary` or the `rfind('<')` approach. Add a unit test with multi-byte text across the hold boundary.

## 5. Rust Backend

### HIGH: The Copilot process lock is held for a whole chat turn, so tool calls, confirmations and context replies cannot get through
**File:** `src-tauri/src/commands/copilot_lsp.rs:1212` (also `:1120` for `conversation_create`; replies blocked at `:1327`, `:1349`, `:1371`)
`copilot_lsp_conversation_turn` and `copilot_lsp_conversation_create` take `state.process.lock().await` and keep it while awaiting the `conversation/turn` / `conversation/create` response. That response only arrives at the end of the turn; the frontend comment at `src/hooks/useCopilotChat.ts:782` confirms "create/turn block until after all $/progress notifications are delivered".
- During the turn, the server sends `conversation/invokeClientTool`, `invokeClientToolConfirmation` and `conversation/context` requests (`copilot_protocol.rs:312-395`).
- The frontend answers them through `copilot_lsp_tool_result`, `copilot_lsp_tool_confirmation_response` and `copilot_lsp_context_response`. Each of these first does `state.process.lock().await`, so each waits behind the turn that is waiting for it.
- The deadlock only ends when the reader-side timeouts fire. Every client tool call fails after 60 s, every confirmation is auto-dismissed after 30 s, and editor context comes back null after 10 s.
- Inline completions (`:989`), `copilot_lsp_stop` and every other Copilot command are also blocked for the whole turn.

This affects every tool-using Copilot chat and agent task (`src/hooks/agent-task/copilot-lsp.ts`).
**Fix:** Hold the outer lock only long enough to clone what the call needs (e.g. `transport.clone_handle()` and an `Arc` of `pending_server_requests`), then release it before `send_request(...).await`. A cleaner option is to store `pending_server_requests` in `CopilotLspState` itself, outside the `Option<CopilotLspProcess>` mutex, so the reply commands never touch the process lock.

### HIGH: The stderr pipe of a running MCP stdio server is never read, so a server that logs enough will freeze
**File:** `src-tauri/src/commands/mcp/mod.rs:97`
`mcp_start_server` spawns the server with `.stderr(Stdio::piped())` but never calls `child.stderr.take()`. The `Child`, with its unread pipe, is stored in `McpServerHandle`; only stdin and stdout are taken.
- MCP servers are told by the spec to log to stderr, and many log every request.
- Once about 64 KB of output builds up in the pipe (the macOS pipe buffer), the server's next stderr write blocks forever.
- A blocked server stops answering on stdout, so tool calls hang. Combined with the next finding, they never return.

The validation path (`:244`, `:284`) takes and drains stderr correctly; only the long-lived path is wrong.
**Fix:** After spawning, take stderr and drain it line by line into the log with a bounded tail, as `copilot_lsp.rs:308-327` and the ACP agent thread already do. Alternatively use `Stdio::null()`, but that loses diagnostics.

### MEDIUM: MCP stdio requests have no timeout, and in-flight requests are never failed when the server dies
**File:** `src-tauri/src/commands/json_rpc.rs:343-357`; `src-tauri/src/commands/mcp/transport.rs:39-52`, `:90-103`
`JsonRpcTransport::send_request` inserts a oneshot sender into `pending` and then waits on `rx.await` with no timeout. Three problems follow:
- When the MCP reader loop exits on a fatal error (EOF, process died, invalid UTF-8), it returns without draining `pending`. The transport in `McpServerHandle` still holds an `Arc` to the map, so the senders are never dropped. Any request in flight when the server crashes waits forever.
- `mcp_start_server` calls `mcp_initialize` (`mod.rs:131`) with no timeout. A stdio binary that never speaks MCP leaves the start command, and the "starting" status, hanging forever. The validate path does wrap this in `MCP_VALIDATE_TIMEOUT`.
- `mcp_call_tool` (`mod.rs:435`) has no timeout, so one hung tool stalls the AI tool loop indefinitely.
- Separately, `send_request` leaks the `pending` entry when `write_message` fails.

**Fix:** In the reader loop's Fatal branch, call `pending.lock().await.drain()` so every waiter gets "server exited". Wrap `send_request` in `tokio::time::timeout`, configurable per call (initialize around 30 s, tools/call longer), and remove the entry on timeout or write error.

### MEDIUM: A body-read timeout in `read_next_message` corrupts the message framing
**File:** `src-tauri/src/commands/json_rpc.rs:410-424`
If `read_exact(&mut body)` is cut off by the 30 s timeout part-way through a body, the function returns `ReadMessageResult::Timeout` and both callers retry (`mcp/transport.rs:87`, `copilot_protocol.rs:82`).
- The bytes already read are discarded, so the next `read_content_length` starts in the middle of a JSON body.
- That message is lost, and the stream usually goes Fatal ("Invalid UTF-8" or a bad header) or skips messages silently.
- This happens when a large tool result arrives slowly, or when the peer pauses mid-write for more than 30 s.

**Fix:** Do not let a timeout cancel the body read. Once a header has been read, either read the body without a timeout (the size cap already bounds it), or keep the partial buffer across retries. Treat a timeout after a valid header as Fatal, not Timeout.

### MEDIUM: When ACP initialize times out, the agent thread, the child process and the network proxy are left running
**File:** `src-tauri/src/commands/acp/mod.rs:197-206`; `src-tauri/src/commands/acp/agent_thread.rs:797`
On the 30 s init timeout, `acp_agent_spawn` calls `cmd_tx.try_send(AgentCmd::Stop)` and returns an error. But the agent thread is still blocked in `conn.send_request(init_req).block_task().await`, and the command loop that would read `Stop` has not started yet.
- The usual cause is a binary that does not speak ACP but waits on stdin, as the error message itself suggests.
- The thread and the child stay alive for the rest of the session, together with the per-instance network proxy started at `mod.rs:147`.
- The handle was never put into `state.agents`, so `AcpState::stop_all_sync` at exit does not see it. `kill_on_drop` never runs, because the runtime is never dropped.
- The child is only killed at the next launch, by the PID-file orphan sweep.

**Fix:** On timeout, SIGKILL the child through the shared `child_pid` atomic (as `acp_agent_reconnect` does). Also put a timeout on the init request inside the agent thread, so the thread exits and runs its proxy, PID-file and profile cleanup.

### MEDIUM: `acp_agent_stop` can hang forever behind an awaited agent request
**File:** `src-tauri/src/commands/acp/mod.rs:329-335`; `src-tauri/src/commands/acp/agent_thread.rs:840-887`
The agent command loop handles commands one at a time and awaits most of them: Authenticate, NewSession, LoadSession, SetMode, ListSessions, Resume, Fork. None of these have a timeout on the thread side, and `acp_agent_authenticate` (`mod.rs:276`) has none on the command side either. Only Prompt is spawned off the loop.
- If the agent stalls on one of these, for example an auth method waiting on a browser flow that never finishes, every later command queues behind it, including `Stop`.
- `acp_agent_stop` waits for the Stop reply with no timeout and does not use the PID-kill fallback that reconnect and exit use.
- The frontend's stop call never returns, and the agent stays alive.

**Fix:** In `acp_agent_stop`, SIGKILL `handle.child_pid` first (or after a short `timeout(reply_rx)`), then join the thread. Add timeouts to the awaited handlers, or spawn them like `handle_prompt`.

### MEDIUM: Two concurrent `start_local_server` calls each spawn a llama-server, and the first one is orphaned
**File:** `src-tauri/src/commands/local_inference.rs:396-443`, `:607-611`
Nothing makes start serialized. Two concurrent calls (for example chat auto-start and the Local Agent setup) can both miss the reuse check, both run `kill_server_process` on the same old PID, and both spawn a server.
- The second call overwrites `server_pid`, `port` and `.server.pid`. The first server, which holds gigabytes of model weights, is no longer tracked.
- `stop_local_server` and `stop_sync` at exit cannot kill it.
- Its `Child` sits inside a `tokio::spawn(child.wait())` task, so `kill_on_drop` cannot fire while the app runs.

**Fix:** Add a `tokio::sync::Mutex<()>` start/stop lock to `LocalInferenceState` and hold it for the whole of `start_local_server`, `stop_local_server` and the completion-server equivalents. Better still, keep the `Child` in state (the skill's "kill_on_drop completeness" advice) instead of moving it into a wait task.

### MEDIUM: The calibration server's pipes are never read, its RSS sampler thread leaks on error, and its HTTP client has no timeout
**File:** `src-tauri/src/commands/model_fit/calibration.rs:73-76`, `:93`, `:113-125`, `:143-162`
`measure_model_runtime` spawns llama-server with stdout and stderr piped but never reads them; llama-server writes its load banner, KV metadata and per-request timings to stderr. Problems:
- Once the pipe fills, the server can block mid-request.
- The `reqwest::Client::new()` used for the warm-up and decode requests has no timeout, so the command can hang forever.
- The early returns via `?` at `:157` (decode request) and `:161` (JSON parse) skip `stop.store(true)`. The sampler thread then keeps spawning `ps` every 100 ms for the rest of the app's life.
- The calibration child is in no managed state and has no PID file, so a crash or exit mid-calibration leaves an untracked llama-server.

**Fix:** Use `Stdio::null()` or drain the pipes. Give the client a timeout. Put `stop.store(true)` in a drop guard so every exit path stops the sampler.

### MEDIUM: The completion server still buffers all of its output for its whole life
**File:** `src-tauri/src/commands/local_inference.rs:952-964`
The main chat server was fixed to drain its output into a bounded 400-line tail, because the old `wait_with_output` collected the whole session's output in memory. The FIM completion server still does `tokio::spawn(child.wait_with_output())`. That buffers all stdout and stderr (per-request timing lines) without limit for as long as it runs, on a machine already short of RAM because of the model weights.
**Fix:** Reuse `spawn_log_drain` plus `child.wait()`, as the main server does at `:629-655`.

### MEDIUM: In skill scripts, the timeout covers only `wait()`, not the output readers
**File:** `src-tauri/src/commands/script_exec.rs:217-221`, `:229-238`
`tokio::time::timeout(timeout, child.wait())` bounds only the direct child. In the success branch, `stdout_task.await` and `stderr_task.await` have no timeout.
- A script that leaves a background process holding the pipes open (`server &`, `nohup`, a daemonising tool) makes the command hang until that process exits, possibly forever, even though the script itself finished.
- On the timeout branch, `child.kill()` signals only the direct child. Grandchildren survive and the reader tasks are left running, neither awaited nor aborted.

**Fix:** Wrap the reader awaits in the remaining time budget and abort them on expiry. Spawn the script in its own process group (`process_group(0)`) and kill the group (`kill(-pgid)`) on timeout.

### MEDIUM: Git commands run blocking `std::process::Command::output()` with no timeout inside async commands
**File:** `src-tauri/src/commands/git.rs:3`, `:51-54`, `:127`, `:297-302`
Every git command is an `async fn` that calls synchronous `std::process::Command::output()` directly on a tokio worker, with no `spawn_blocking` and no timeout.
- `git commit` can block indefinitely on a slow pre-commit hook or on a GPG/pinentry signing prompt.
- `git status` takes seconds on large repositories.
- Each such call holds a runtime worker. A few at once starve the shared runtime that ACP, AI streaming and index commands also use.

**Fix:** Use `tokio::process::Command` with `tokio::time::timeout`, or wrap the calls in `spawn_blocking`.

### MEDIUM: Full reindexes run on tokio workers while holding the index locks
**File:** `src-tauri/src/index/mod.rs:606-611`, `:625-636`, `:1059-1068` (`index_init`, `index_rebuild`, `index_file`)
`index_init` and `index_rebuild` are `async fn` but do a whole-directory walk, parse and SQLite write (`reindex_directory`) synchronously. They do this while holding the `parking_lot` lock on `project_dbs` or `global_db`.
- Every other index command (search, `index_file`, stats) then does a blocking `lock()` on another tokio worker. On a large vault this ties up several runtime workers at once and stalls unrelated async commands.
- `parking_lot` is the right choice here (no poisoning, consistent global→projects lock order), but it should not be locked from async workers during long work.

**Fix:** Run the bodies inside `tokio::task::spawn_blocking`. The `State` would need to be accessed through `app.state()` inside the closure, since it cannot be moved in directly.

### MEDIUM: Stored llama-server PIDs are signalled after the process may already have exited, with no identity check
**File:** `src-tauri/src/commands/local_inference.rs:607-611`, `:635-655`, `:710-716`, `:251-264`
If llama-server crashes (for example from OOM), the `child.wait()` task reaps it, but `server_pid` (and `.server.pid`) keep the old PID. The next `start_local_server`, `stop_local_server`, or `stop_sync` at exit then runs `terminate_with_escalation(pid)`, which sends SIGTERM and then SIGKILL. It does not check identity; only the startup orphan path does (`should_signal_pid`). The same applies to `completion_server_pid`. PID recycling within a session is unlikely but possible, and the result would be a SIGKILL to an unrelated process.
**Fix:** In the wait task, clear `server_pid` (if it still equals this PID) and remove the PID file when the child exits. Alternatively, run the `should_signal_pid(process_cmdline(pid), "llama-server")` check inside `kill_server_process`.

### MEDIUM: `get_shell_path` runs an interactive login shell with no timeout, and every spawn path waits on it
**File:** `src-tauri/src/commands/shell_path.rs:20-27`
`$SHELL -il -c 'echo $PATH'` runs synchronously inside `OnceLock::get_or_init`, with no timeout. It is called right before spawning ACP agents, MCP servers, Copilot and llama-server, mostly from async contexts.
- A slow or stuck rc file (nvm, conda, an oh-my-zsh update prompt, a network-mounted home) blocks the first caller's tokio worker.
- Every concurrent caller then blocks on the `OnceLock` too, so every subprocess spawn in the app hangs.

**Fix:** Run it with a timeout of about 5 s: `tokio::process` plus `timeout`, or a thread plus `recv_timeout` with a kill. Set `stdin(Stdio::null())`, and fall back to the inherited PATH on timeout. Ideally warm it once at startup on a blocking thread.

### LOW: Agents silently run without the sandbox or network confinement if setup fails
**File:** `src-tauri/src/commands/acp/mod.rs:165-171`; `src-tauri/src/commands/acp/agent_thread.rs:611-616`; `src-tauri/src/commands/script_exec.rs:249-258`
If the network proxy fails to start (port bind error), the agent is spawned without network confinement. If `sandboxed_command` errors, the agent is spawned with no sandbox at all. The skill-script path makes the same choice. Each case is only logged at warn level, and the frontend is still told what it asked for. Passing `sandbox_enabled: sandbox` back in `SpawnResult` reports the request, not the result. This is a fail-open trust decision; it is flagged here for the security audit.
**Fix:** Fail closed, or return the confinement actually in force in `SpawnResult` and show it in the UI.

### LOW: Blocking kill and join calls run on async workers
**File:** `src-tauri/src/commands/process_guard.rs:65-78`; `src-tauri/src/commands/acp/mod.rs:373-385`
`terminate_with_escalation` sleeps up to 500 ms and spawns `kill` and `ps` processes. It is called directly from async commands (`start_local_server` → `kill_server_process`, `stop_local_server`, the completion-server commands). `acp_agent_reconnect` blocks on `done_rx.recv_timeout(500ms)` inside an async fn. Each of these parks a tokio worker for up to 0.5 s. `acp_agent_stop` already does this correctly with `spawn_blocking`.
**Fix:** Wrap these calls in `tokio::task::spawn_blocking`.

### LOW: A PID of 0 would send `kill -15 0`, which signals the whole process group, including Notesage
**File:** `src-tauri/src/commands/local_inference.rs:605`, `:925`; `src-tauri/src/commands/process_guard.rs:65`
`child.id().unwrap_or(0)` stores 0 in `server_pid` if `id()` returns `None`. A later `terminate_with_escalation(0)` runs `kill -15 0`, and then `kill -9 0` because `process_alive(0)` is true. That signals Notesage's own process group. In practice `id()` is `Some` right after spawn, so this cannot happen today, but nothing guards it. The ACP code does guard with `pid != 0`.
**Fix:** Return an error if `id()` is `None`. Make `terminate_with_escalation` and `process_alive` refuse PIDs of 1 or less.

### LOW: The Copilot language server is not stopped on `RunEvent::Exit`
**File:** `src-tauri/src/lib.rs:629-641`
The exit hook stops ACP, the network proxy, MCP, local inference and the sandbox monitor, but not `CopilotLspState`. The LSP child relies on `kill_on_drop`, which does not run at process exit. It probably shuts itself down through its `processId` watchdog (sent in `initialize`, `copilot_lsp.rs:352`), and it has no PID file for startup recovery. The skill asks for exhaustive exit cleanup.
**Fix:** Add a sync stop: `try_lock` the process, then `child.start_kill()`.

### LOW: The exit cleanup skips everything if a lock is busy at that moment
**File:** `src-tauri/src/commands/acp/state.rs:39-45`; `src-tauri/src/commands/mcp/state.rs:60-66`; `src-tauri/src/commands/network_proxy.rs:194`
Each `stop_all_sync` does `try_lock()` on its map and returns at once if the lock is held. For example, `mcp_start_server` holds the lock briefly, and `check_processes` holds it during the health poll. If exit happens at that moment, no agents or servers are killed. ACP has the PID-file sweep at next launch; MCP has no PID-file recovery.
**Fix:** Retry `try_lock` a few times with a short sleep, or keep a parallel PID list in an atomic or `parking_lot` structure for the exit path.

### LOW: The sandbox monitor can stop for good, and agent PIDs can stay registered after the agent exits
**File:** `src-tauri/src/commands/sandbox_monitor.rs:72-80`, `:150-158`; `src-tauri/src/commands/acp/agent_thread.rs:948-954`
When `log stream` ends ("Log stream ended unexpectedly"), the loop breaks but `running` stays true, so the monitor is never restarted and later violations are not reported. Separately, the agent thread removes its PID with `agent_pids.try_lock()`. If the monitor holds the lock at that moment, the stale PID stays registered, and a recycled PID could have violations attributed to a dead agent.
**Fix:** Reset `running` when the stream loop exits. Do the PID removal inside the temporary runtime already built for proxy cleanup, using `lock().await`.

### LOW: Whisper context lock held across whole-file inference (from the 2026-07-03 audit, still present), plus a model-swap race between its two locks
**File:** `src-tauri/src/commands/transcription.rs:965`, `:987`
The `parking_lot` lock is still held across `create_state()` and `full()`, so concurrent `transcribe_file` jobs are serialized. This is deliberate and documented. New: the model-load lock is released at about `:980` and taken again at `:987`. A concurrent job asking for a different model can swap the cached context in between, so this job transcribes with the wrong model; nothing checks that `cached_model == model_task` on the second lock.
**Fix:** Do the load and the inference under a single lock acquisition, or check the model id again after taking the second lock.

### LOW: iOS `fetch_page_html` has no private-IP guard and reads the whole body without a cap
**File:** `src-tauri/src/commands/preview.rs:207-220`
This iOS-only command fetches a URL supplied by the caller with default redirect handling, no `net_guard::is_blocked_ip` check, and an unbounded `res.text()`. It returns the whole body to the WebView. That is an SSRF read channel to the device's LAN and a memory-exhaustion path, against the pattern in `link_preview.rs`.
**Fix:** Reuse link_preview's per-hop guarded fetch and its 2 MiB streamed cap.

### LOW: Error-response bodies from AI providers are read without a cap
**File:** `src-tauri/src/commands/ai.rs:347` (and about 14 sibling sites); `ai_streaming.rs:210`, `:520`, `:796`, `:1057`; `local_inference.rs:1221`, `:1529`, `:1673`; `mcp_oauth.rs:535`
`response.text().await.unwrap_or_default()` reads non-2xx bodies without limit. The peers are user-configured provider endpoints, so the risk is low, but a misbehaving proxy or custom endpoint can return a very large error page that then flows into error strings and the frontend.
**Fix:** One shared `read_body_capped(resp, 64 KiB)` helper; `mcp/transport.rs:137` already has a suitable one.

### LOW: Regexes are recompiled on every export call
**File:** `src-tauri/src/export/markdown_to_html.rs:141`, `:321`, `:369`, `:381`, `:399`, `:429`, `:474`, `:505-552`; `src-tauri/src/export/table_utils.rs:27`, `:87`
About 15 `Regex::new(...).unwrap()` calls run on every invocation, and some run inside per-table or per-row loops (`:552`). The patterns are constants, so they cannot panic, but recompiling them is wasted CPU. `index/parser.rs` already uses `LazyLock` for this.
**Fix:** Move them to `static LazyLock<Regex>`.

### Confirmed Good Patterns
- **Prior findings now fixed:**
- Proxy request head: `read_request_head` loops until `\r\n\r\n` with a cap (`network_proxy.rs:294`).
- `run_in_terminal`: argv-bound osascript with no escaping (`dialog.rs`).
- llama-server orphan cleanup: verified with `should_signal_pid(process_cmdline)` before signalling (`local_inference.rs:807`).
- Node.js and GitHub binary downloads: SHA-256 checked against SHASUMS (`agent_manager.rs:787-796`, `:1441`).
- Download buffers: `MAX_PREALLOC_BYTES` clamp plus `download_capped(MAX_DOWNLOAD_BYTES)`.
- Body caps: MCP HTTP body (8 MiB, `mcp/transport.rs:135`), web search body (4 MiB), skill-script output (4 MiB, drained past the cap).
- `render_markdown_preview` now runs in `spawn_blocking`.
- ACP `pkill -f` replaced by PID files with identity checks (`acp/state.rs:140-195`); a reconnect cannot delete the new spawn's PID file.
- Shared `net_guard::is_blocked_ip` used by both `mcp_oauth` and `link_preview`.
- `kill_server_process` now escalates SIGTERM to SIGKILL.
- **GGUF parser:** 10 MB string cap, `MAX_GGUF_ARRAY_DEPTH` recursion bound, caps on array and KV counts.
- **JSON-RPC framing:** `MAX_MESSAGE_BYTES` (64 MiB) is enforced before `vec![0u8; n]`; `MAX_HEADER_BYTES` caps headers.
- **Mutex types:**
- `parking_lot::Mutex` in `index/` and `watcher`, with a consistent global→projects lock order (no nesting inversions found).
- Whisper context uses `parking_lot`, with the rationale documented.
- Tokio `Mutex` for async lifecycle state (`acp`, `mcp`, `network_proxy`, `copilot`, local-inference port and model).
- **Std `Mutex` `.lock().unwrap()` sites** (`local_inference.rs:305/315/321/610/927`, `ai.rs:28/37/42`, `typst_world.rs:74/80/125/133/137`): every guarded section is a plain HashMap or Option operation that cannot panic, so poisoning is not reachable. Other std-mutex sites use `if let Ok` or `unwrap_or_else(|e| e.into_inner())` (tray, transcription, html_preview, ACP stderr tail).
- **ACP:** `stop_all_sync` does a PID SIGKILL plus a 500 ms bounded join. `acp_agent_stop` and `acp_agent_reconnect` take the handle out of the map before any await. Each ACP command clones `cmd_tx` and releases the lock right away. Prompts are spawned off the command loop and have a 30-minute ceiling. The stderr tail is a bounded ring buffer.

### HIGH: The AI tool path-scope check can be bypassed with `..` or a relative path, and `read_file`/`list_directory` run without a prompt
**File:** `src/lib/ai/path-filter.ts:125`
- **Root cause:** `isPathAllowed` does a raw `startsWith(root + '/')` with no normalisation. So `/tmp/../Users/<u>/.ssh/id_rsa` (any entry in `SYSTEM_PREFIXES`) and `<projectRoot>/../../.aws/credentials` both pass.
- **Relative paths skip the check entirely:** `extractPathsFromStructuredInput` (`:77`) only collects values starting with `/`. A path like `Users/<u>/.ssh/id_rsa` is not checked at all. The backend `read_file` (`src-tauri/src/commands/file.rs:27`) then resolves it against the process working directory, which is `/` for a Finder-launched macOS app.
- **Allowed by design:** `SAFE_HOME_DIRS` (`:37`) also makes `~/.config` readable, which includes `~/.config/gh/hosts.yml` (GitHub tokens).
- **Why this matters:** this filter is the *only* boundary for direct-API and Copilot tool calls. `executeToolCall` runs in the main process with no Seatbelt sandbox (`src/lib/tool-executor.ts:227`, `:272`). `read_file`, `list_directory` and `web_search` are auto-allowed (`src/stores/permission-store.ts:671-678`).
- **Attack:** instructions hidden in a document or a search result can make the model silently read SSH or cloud keys. The model can then send them out through an auto-allowed `web_search` query, or they simply go to the LLM provider. Writes through `write_file` (for example `/tmp/../Users/<u>/.zshrc`) go through the same broken check; they need one approval, but the approval card shows a path that looks harmless.
- **Context:** the file header says it does not defend against prompt injection, but `docs/architecture.md:402` presents the tool-executor gating as the real boundary for agents.

**Fix:**
- Resolve to a canonical absolute path before checking: reject relative and `~` paths, collapse `..`, and ideally `realpath` on the Rust side.
- Add a backend-enforced root check for AI-originated reads and writes.
- Separate the read and write allow-lists, and drop `.config` (or limit it to specific tool subdirectories).
- Stop auto-allowing `web_search` when the conversation contains file content.

### HIGH: The Seatbelt profile grants unrestricted `mach-lookup` and `/var/run` unix sockets, opening DNS and launch-services escape routes
**File:** `src-tauri/src/commands/sandbox.rs:453` (also `:295-297`)
- **What the profile says:** the sandbox profile for ACP agents (and skill scripts) ends with a bare `(allow mach-lookup)`. The kernel-network-deny block also allows `(remote unix-socket (subpath "/var/run"))`, `/private/var/run` and `AF_UNIX` sockets.
- **DNS is not actually blocked:** the code comments (`:266`, `:284`) say "DNS is blocked — resolution happens through the proxy". But an open mach-lookup plus `/var/run/mDNSResponder` lets an agent resolve names directly. That means it can send data out through DNS lookups (`<data>.attacker.tld`) that the domain allowlist never sees.
- **Launching apps outside the sandbox:** unrestricted mach-lookup also reaches launch services (`launchservicesd`, `open`/`NSWorkspace`). An agent can then start an app or a `.command` file that runs **outside** the sandbox, under launchd, with full file and network access. This is a known escape route for `sandbox-exec`.
- **Other sockets:** the `/var/run` socket allow can also reach daemons such as `docker.sock` where those sockets exist.
- **Status:** the 2026-07-05 audit marked sandbox integrity "Safe". This is new and was missed then.

**Fix:**
- Replace `(allow mach-lookup)` with an explicit `(global-name …)` allowlist covering only what Node/Go agents need (trustd, cfprefsd, notifyd, and so on). Exclude `com.apple.dnssd.service`, `com.apple.coreservices.launchservicesd` and `com.apple.lsd.*`.
- Narrow the unix-socket allow to named literals.
- Add a test that checks the generated profile for these.

### HIGH: Files an agent can write are later run by the unsandboxed main process (escape chain)
**File:** `src-tauri/src/commands/acp_binary.rs:177`; `src-tauri/src/commands/agent_manager.rs:681,707,1005`; `src-tauri/src/commands/git.rs:50`; `src-tauri/src/commands/sandbox.rs:46,427`

Every sandboxed agent can write to `~/.notesage` (`sandbox.rs:46`) and `~/.config` (`sandbox.rs:427`). The main process later runs code from both places **outside** the sandbox:

1. **`acp_agent_check_availability`** runs `<binary> --version` with `std::process::Command`, no sandbox. The binary is resolved first from `~/.notesage/agents/bin/` (`acp_binary.rs:60-66`). It runs whenever the Connect Agent settings view opens (`src/components/settings/ConnectAgent.tsx:72`). An agent that overwrites `~/.notesage/agents/bin/codex-acp` gets its code run unsandboxed.
2. **`is_node_runtime_available`, `download_node_runtime` and `do_npm_install`** run `~/.notesage/runtime/node/bin/node` and `npm` unsandboxed (`agent_manager.rs:681`, `:707`, `:965`, `:1005`).
3. **Git config:** an agent can write `~/.config/git/config` (git reads the XDG location) with `core.fsmonitor = "<cmd>"`, a pager, or a textconv driver. The app runs `git status` automatically on every opened root (`src/hooks/useGitRepoDetection.ts:50` → `git.rs:50`), with no sandbox. The `.git` write-deny rule (`sandbox.rs:441`) only protects per-repo config.

This is the same "agent-writable → spawn" class the skill tells auditors to trace (C1). MCP was mitigated with disabled-by-default; these routes have no mitigation.

**Fix:**
- Make `~/.notesage/agents/bin`, `~/.notesage/agents/lib`, `~/.notesage/agents/dist` and `~/.notesage/runtime` read-only inside the sandbox (add explicit `deny file-write*` after the allow rule). Do the same for `~/.config/git`, or drop the blanket `~/.config` write.
- Verify managed binaries against a recorded hash before any unsandboxed run, or run the `--version` probes inside the sandbox.
- Run git with `-c core.fsmonitor=false`, and use `--no-ext-diff --no-textconv` for `git diff`.

### MEDIUM: HTML viewer "allow scripts" mode reads any file through `./../` and the framed page can send it out
**File:** `src/components/editor/viewers/HtmlViewer.tsx:287-292`
- **The bug:** the local-script inliner matches `src=["'](\.\/[^"']+)`, which also matches `./../../../.ssh/id_rsa`. It builds `${dir}/${rel}` and calls `read_file`, which does no path validation. It then inlines the file contents as `<script>…</script>`.

- **Status:** new.

**Fix:**
- Resolve each path, reject `..`, and require the result to be inside the HTML file's directory (canonicalised, in Rust).
- Consider a restrictive CSP header on `htmlpreview` responses for the allow-scripts path (for example `connect-src 'none'`).

### MEDIUM: "Always allow" for skill scripts in chat is per tool name, not tied to content, and applies everywhere
**File:** `src/hooks/useDirectApiChat.ts:391,459`; `src/lib/tool-executor.ts:309-316` (and `executeSkillTool` `:122-129`)

### HIGH: MCP import from VS Code is entirely broken — the new guard rejects the source string Rust actually sends
**File:** `src/lib/mcp/config-guards.ts:35-41` (with `src-tauri/src/commands/mcp/types.rs:99-107`, `src/hooks/useMcpOperations.ts:25,83,251`)
`McpConfigSource` is `#[serde(rename_all = "snake_case")]` and has no per-variant rename. That means `VsCode` goes over the wire as `"vs_code"`. The frontend union and `MCP_SOURCES` expect `'vscode'`. `mcp_import_configs` for source `vscode` (`config.rs:136`) tags every entry `McpConfigSource::VsCode`, so `isImportedMcpConfig` returns false for all of them. `ImportDialog` then shows "Skipped N malformed server entries from vscode" and imports nothing.

This is a regression from fixing the prior audit's MEDIUM-HIGH. The old unvalidated path ignored `source` and used `sourceId`. The project already knows this pitfall: `AIProviderType` uses explicit `#[serde(rename = "openai")]`. Neither `config-guards.test.ts` nor `ImportDialog.test.tsx` has a VS Code case. Note that `source_prefix()` returning `"vscode"` is a different code path, so its Rust test passes.
**Fix:** Add `#[serde(rename = "vscode")]` to `VsCode`. Alternatively, accept `'vs_code'` in `MCP_SOURCES`/`mapSource`, but the Rust rename is preferable because `mcp.json` and the TS unions already use `vscode`. Add a Rust serialization test (`serde_json::to_string(&McpConfigSource::VsCode) == "\"vscode\""`) and a guard test with a real Rust-shaped fixture. Longer term, generate the TS union from the Rust enum (ts-rs/specta).

### MEDIUM: `friendlyAIError` can itself throw, leaving the chat stuck in a loading state
**File:** `src/lib/ai/errors.ts:152-158`
`JSON.parse(jsonMatch[0])` returns implicit `any`. `msg = parsed?.error?.message || parsed?.message || ''` assigns whatever is there to a `string`-typed variable.

If a provider or OpenAI-compatible server sends a non-string `message` (object, number, array):
- `msg.startsWith` throws inside the try, and the catch keeps `msg` as the object.
- Then `mapAIError(friendly)` / `friendly.toLowerCase()` (`:181,189`, `getErrorHint :246`) throws a TypeError out of the error formatter.

The callers are `useDirectApiChat.ts:655,769` and `useCopilotChat.ts:813`. They call it inside their `catch` before `setLoading(false)` / `runError()`, so the chat stays stuck in loading and the real error is lost. This is new and was not covered in July.
**Fix:** Do `const parsed: unknown = JSON.parse(...)`, then extract with `typeof x === 'string'` checks for `error.message`, `message` and `detail` (same for `inner`). Fall back to the raw string otherwise.

### MEDIUM: Remote `changelog.json` (network data) stored unvalidated; a shape change crashes the app outside the error boundary
**File:** `src/hooks/useChangelog.ts:110,124`
`const data = await res.json()` (implicit `any`) goes straight into `setChangelog(data)` typed as `Changelog`. The remote fetch comes from GitHub `releases/latest`, and a valid result replaces the bundled copy.

Consumers do not guard the shape:
- `getChangesBetween` → `changelog.releases.filter(...)` and `compareVersions(r.version, …)`.
- `ChangelogDialog.tsx:160,163` → `changelog.releases.length`.
- `UpdateDialog` → `release.sections.features`.

Any future format change, or a JSON response without `releases`, throws in render. Older clients always read the latest file, so this is a forward-compatibility trap. `UpdateDialog` is mounted at `App.tsx:796`, after the `Workspace` ErrorBoundary closes (`:768`), so a throw there blanks the app.
**Fix:** Add an `isChangelog(v: unknown)` guard (releases array; each entry has string `version`/`date` and an object `sections` with string-array fields). Drop bad entries, and keep the bundled copy when the remote copy fails validation.

### MEDIUM: Agent-written pending-comment files asserted to `PendingCommentFile`; malformed input gives unhandled rejections or corrupt comments
**File:** `src/lib/pending-comments.ts:110` (also `:126`, `:139`, `:179-245`, `:274`, `:300`)
`pending = JSON.parse(raw) as PendingCommentFile` parses model-generated JSON that ACP agents write to `.notesage/pending-comments/`. Only `Array.isArray(comments/resolve)` and a truthy `file` are checked. Failure cases:
- If the JSON is `null`, `pending.status` throws.
- If `file` is a non-string, `pending.file.startsWith` throws.
- A `null` element in `comments` throws on `c.anchor_text`.
- A non-string `anchor_text` throws in `stripMarkdownSyntax(...).replace`.
- A non-string `body` (e.g. an object) is persisted as a comment body and fails later at render.
- `resolve!` elements are unchecked.

The caller `useFileWatcher.ts:211` fires `processPendingCommentFile(path, projectRoot)` with no `.catch`. A throw is therefore an unhandled rejection, the file is never marked `processed`, and it is retried on every modify. July did not flag this site.
**Fix:** Parse to `unknown` and add an `isPendingCommentFile` guard with per-comment filtering (string `anchor_text`/`body`, optional integer `occurrence`, string `resolve` IDs). On failure, write back `status: 'processed'` with a reason. Add `.catch(log)` at the call site.

### MEDIUM: Library-migration undo record shallowly validated before driving file moves and deletes
**File:** `src/lib/library-migration-undo.ts:185-186` (consumed at `:84-121`)
`JSON.parse(...) as UndoRecord` only checks `typeof id === "string"` and `Array.isArray(moves)`. `undoLibraryMigration` then builds paths from `record.oldRoot`, `record.newRoot`, `move.from/to`, `item.root/path/content`, and calls `moveEntry`, `writeFile` and `deletePath`.

- A record from another app version, or a hand-edited one, missing `oldRoot`/`newRoot` gives `"undefined/<rel>"` move targets.
- `item.path: ""` with `content: null` gives `deletePath("<newRoot>/")`, a deletion of the library root.
- A missing `destroyed` throws at `:84`.

The data is local and app-written, so this is an edge case. But it is the most destructive unvalidated boundary in the repo.
**Fix:** Write a full `isUndoRecord` guard: non-empty absolute roots, every move/destroyed entry has non-empty relative string paths, `root ∈ {"old","new"}`, and `content` is a string or null. Reject `""`, `..` segments and leading `/` in relative paths.

### HIGH: The ACP stdout filter `JsonLineFilter` has no tests and stalls permanently on a partial non-JSON line
**File:** `src-tauri/src/commands/acp_client.rs:292`
Every agent's stdout passes through this filter (`agent_thread.rs:721`). It exists to strip non-JSON output such as Gemini CLI's "interactive prompts". No test in `src/` or `tests/` covers it.
- **The stall:** when the `BufReader` holds a chunk with no newline that does not start with `{` and is at most 4,096 bytes (for example a prompt or progress text written without `\n`), `poll_read` returns `Poll::Pending`. But `poll_fill_buf` had already returned `Ready`, so no waker is registered.
- **Why it cannot recover:** tokio's `BufReader::poll_fill_buf` only refills once its buffer is empty. A re-poll sees the same bytes and returns `Pending` again. The ACP reader stops for good, and the agent looks "unresponsive" with no error.
- **The oversized branch** (line 285, more than 4,096 bytes) also falls through to `Pending` without a waker.
The skill's "Agent lifecycle" flow hides this: `tests/mock_acp_agent.rs` drives the `agent_client_protocol` crate directly over a `Channel`, never through the app's filter or `run_agent_thread`.
**Fix:** Add `#[tokio::test]` cases that feed `tokio_test::io::Builder` / `tokio::io::duplex` scripted reads:
- a non-JSON prefix without newline, followed later by the rest plus a JSON line
- non-JSON content over 4 KB
- a JSON line split across reads
- JSON plus leftover bytes when the caller's `ReadBuf` is small
Then fix the code: keep a private line buffer and read from the inner reader directly, rather than returning `Pending` after a `Ready` fill.

### HIGH: Streaming chunk decoding has no tests and corrupts multibyte UTF-8 split across network chunks
**File:** `src-tauri/src/commands/ai_streaming.rs:229` (also `:536`, `:809`, `:1074`; `src-tauri/src/commands/local_inference.rs:1280`)
All four provider streams (Anthropic, OpenAI, Ollama, OpenAI-compatible) and llama-server streaming run `String::from_utf8_lossy(&bytes)` on each `bytes_stream()` chunk before buffering. A UTF-8 character split across a chunk boundary (å/ä/ö, CJK, emoji) becomes U+FFFD inside the SSE `data:` JSON. That corrupted text is then emitted as `ai-stream-chunk` and can be written into the user's document.
The only SSE tests are 7 helper tests (`test_parse_sse_events_tool_use`, stop-reason and Ollama format). Nothing tests chunk boundaries, `\r\n\r\n` delimiters, multi-line `data:` or tool-argument accumulation across chunks. The skill's "AI streaming (all providers)" flow is therefore covered only by frontend tests that mock the IPC events.
**Fix:**
- Buffer raw bytes (`Vec<u8>`) and decode only complete lines or events. For the trailing partial sequence, use `std::str::from_utf8` with `valid_up_to()`.
- Pull the per-provider loop body into a pure `fn feed(&mut State, &[u8]) -> Vec<Emit>` and test it with chunks split inside a multibyte character, inside `\n\n`, and inside a tool-call JSON argument.

### HIGH: The automations runtime's security-gate wiring has 0% coverage
**File:** `src/hooks/useAutomationRunner.ts:169` (also `:104-130` and `:177`)
`useAutomationRunner` (322 lines, 0% in the baseline, imported by no test) is the only code that connects several protections to unattended runs:

### HIGH: Desktop Recordings view and startup transcription scan can never find a recording
**File:** `src-tauri/src/commands/file.rs:167` (also `src/stores/recordings-store.ts:133`, `src/hooks/useRecordingsInbox.ts:335`)

### HIGH: An unreadable or undownloaded library marker is treated as "no marker", defeating the library follow and the undo
**File:** `src-tauri/src/commands/sync.rs:517-519`, `src-tauri/src/library_marker.rs:81-84`, `src/hooks/useAppLifecycle.ts:337-349`, `src/lib/library-migration-run.ts:286-287`, `src/components/settings/LibraryMigrationDialog.tsx:509-514`

(1) **Startup:** a second Mac whose `.notesage/library.json` has not downloaded resolves to CloudDocs whenever anything is left in the old folder; `library.kind` is not `"container"`, so `followLibraryMove` (ed13368) is skipped and every moved project is removed with "directory no longer exists". **Fix:** Return three states from Rust: `Absent`, `Pending` (placeholder present: `icloud_ensure_downloaded`, wait/retry), `Err`. At startup `Pending`/`Err` keeps projects under both roots (the `containerDenied` "held" path) with a toast. `clearMigrationInMarker` throws on `Pending`/`Err`.
