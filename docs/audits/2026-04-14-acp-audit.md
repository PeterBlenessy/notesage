## Executive Summary

Notesage has a **functional, production-quality ACP integration** that covers the core happy path: spawn agent → authenticate → create session → stream prompts with tool calls and permissions. The implementation includes strong process management (SIGKILL cleanup, PID tracking, reconnect) and a custom `JsonLineFilter` to handle misbehaving agents.

However, the implementation covers roughly **40% of the ACP surface area**. Major gaps include: no thinking/reasoning segment handling in chat, no session modes, no config options, no plan display, no slash command passthrough, no file system/terminal client capabilities, no usage tracking in UI, and no support for any of the newer unstable features (elicitation, NES, session fork/resume/close, session list). Several provider-specific workarounds are hardcoded where ACP provides dynamic alternatives.

**Biggest wins by effort-to-impact ratio:**

1. **Thinking segments in chat** — low effort, high UX impact (already handled in task operations)
2. **Crate version bump** — low effort, unlocks new capabilities
3. **Session modes** — medium effort, enables code/architect/ask switching
4. **Usage tracking display** — low effort, already receiving data
5. **Client FS/terminal capabilities** — medium effort, unlocks faster agent operations

> **Post-implementation update (v0.34.0):** All Phase 1–4 tasks from the PRD have been completed. ACP feature coverage raised from 41% to \~70%. Thinking in chat, session modes, dynamic config options, usage tracking, plan display, slash command passthrough, capability probing, eager session creation, session restoration, and mode-sandbox conflict resolution are all implemented. Remaining gaps are client FS/terminal capabilities and unstable features (NES, elicitation, session fork/resume).

## Detailed Gap Analysis

### 1. Thinking/Reasoning in Chat — ~~HIGH PRIORITY~~ ✅ RESOLVED

**Gap:** `agent_thought_chunk` events are handled in `useAgentTaskOperations.ts` (background agent tasks) but **completely ignored** in `useAcpSessionListeners.ts` (interactive chat). Users see no thinking/reasoning output from Claude Code, Codex, or other agents in the chat panel.

**Resolution:** Added `agent_thought_chunk` handling to `setupAcpChatListeners()`. ThinkingSegments rendered in chat with collapsible UI. Also added dual-write consistency in task operations.

### 2. Crate Version Drift — ~~HIGH PRIORITY~~ ✅ RESOLVED

**Gap:** Using `agent-client-protocol` v0.10.4 and schema v0.11.4 while latest is v0.11.6. The crate is actively evolving.

**Resolution:** Both crates bumped to latest. Unknown `SessionUpdate` variants now handled gracefully with debug logging.

### 3. Session Modes — ~~MEDIUM PRIORITY~~ ✅ RESOLVED

**Gap:** No support for `session/set_mode`. Claude Code supports "code", "architect", and "ask" modes. Other agents may support similar modes. The `modes` field from `session/new` response is not extracted.

**Resolution:** Full implementation: mode picker UI with permission-level mapping (Read Only / Agent / Full Access / Plan), capability probing at connection registration, connection defaults, eager session creation, mode-sandbox conflict dialog.

### 4. Usage Tracking — ~~LOW PRIORITY, FREE WIN~~ ✅ RESOLVED

**Gap:** `unstable_session_usage` feature is enabled in Cargo.toml, but `usage_update` events are completely ignored in the frontend. The data is being received and discarded.

**Resolution:** `usage_update` events parsed and displayed as token count in chat footer with cost tooltip on hover.

### 5. Client FS/Terminal Capabilities — **MEDIUM PRIORITY** (still open)

**Gap:** Notesage advertises no client capabilities (`fs.readTextFile`, `fs.writeTextFile`, `terminal`). This means agents must handle all file I/O and command execution themselves.

**Impact:**

- Agents can't delegate file reads to the client (which already has the files open)
- Agents can't use the client's terminal for command execution
- Agent operations are slower (agent reads files from disk instead of client serving from memory)
- No follow-along editor integration (agent edits files but editor doesn't update)

**Fix:**

1. Implement `Client::read_text_file()` — serve from editor state or filesystem
2. Implement `Client::write_text_file()` — write + update editor
3. Implement `Client::create_terminal()` etc. — delegate to Tauri shell
4. Advertise capabilities in `InitializeRequest`

**Effort:** High (significant new functionality), but high long-term value

### 6. Tool Call Update Handling — ~~MEDIUM PRIORITY~~ ✅ RESOLVED

**Gap:** `tool_call_update` events only update the active tool label. The spec says updates can change: `title`, `kind`, `status`, `content` (array replacement), `locations`, `rawInput`, `rawOutput`.

**Resolution:** Expanded handler to track status transitions, store locations as clickable file links, and display rawOutput in tool result segments. Diff content rendering still not implemented (❌).

### 7. Agent Plan Display — ~~LOW PRIORITY~~ ✅ RESOLVED

**Gap:** `plan` session updates are ignored. Agents like Claude Code send execution plans for complex tasks.

**Resolution:** PlanSegment type added. Plans render as collapsible cards with status icons (pending/in_progress/completed) and priority dots.

### 8. Session Info Updates — ~~LOW PRIORITY, FREE WIN~~ ✅ RESOLVED

**Gap:** `session_info_update` events (containing session `title`) are ignored. Agents generate titles for conversations.

**Resolution:** `session_info_update` handled — agent-generated titles automatically applied to chat history.

### 9. Slash Command Passthrough — ~~LOW PRIORITY~~ ✅ RESOLVED

**Gap:** `available_commands_update` events are ignored. Agents advertise slash commands (e.g., Claude Code's `/compact`, `/clear`, `/bug`, etc.).

**Resolution:** Agent commands stored from `available_commands_update` and surfaced in the `/` command menu alongside Notesage skills, distinguished by Terminal icon.

### 10. Config Options — ~~LOW PRIORITY~~ ✅ RESOLVED

**Gap:** `session/set_config_option` not implemented. Agents provide config options (e.g., thinking effort) via the protocol, but Notesage uses hardcoded UI for these settings.

**Resolution:** Dynamic config options extracted from session response, rendered as dropdowns in chat footer. Mode and model categories filtered (handled by dedicated pickers). Hardcoded Codex `reasoningEffort` migrated to dynamic `acpDefaults.thinkingEffort`.

## Robustness Assessment

### Strengths

1. **Process lifecycle management** is thorough: `kill_on_drop`, PID tracking, `RunEvent::Exit` hook, frontend `beforeunload`, SIGKILL fallback
2. **Reconnect flow** is well-designed: kill old → spawn new → authenticate → load session → resend prompt
3. **Permission handling** is correct: channel-based async wait, proper cancellation on agent stop
4. **JsonLineFilter** is production-quality: handles edge cases (long lines, partial buffers, EOF)
5. **Error recovery** includes one-time auto-retry for connection errors
6. **Network sandboxing** is defense-in-depth: kernel Seatbelt + proxy + domain allowlists

### Weaknesses

1. **No capability checking** — calls `session/load` without checking `agentCapabilities.loadSession`, calls `session/set_model` (implicitly via CLI args) without checking support
2. **Deserialization brittleness** — unknown `SessionUpdate` variants may cause parse errors rather than graceful unknown handling
3. **Single-threaded tokio** — `ClientSideConnection` is `!Send`, forcing a `LocalSet` on a dedicated OS thread. Thread panics silently kill the agent connection
4. **No reconnect on partial failure** — if authenticate succeeds but session/load fails, the agent is in an authenticated but sessionless state
5. **Silent event drops** — `let _ = self.app.emit(...)` in `session_notification()` silently drops events if the window is gone
6. **30-minute hard timeout** — may be insufficient for very long research tasks, but also means a hung prompt blocks the thread for 30 minutes

## Next Batch Planning (2026-04-17)

### Client FS Capabilities — SKIPPED

**Decision:** Skip `fs/read_text_file` (#47) and `fs/write_text_file` (#48) indefinitely. Not worth the complexity.

**Reasons:**

1. **Dual representation mismatch:** The editor holds a ProseMirror document tree, not raw markdown. Serving "file content from memory" requires serializing ProseMirror → markdown on every agent read request — slower than the agent reading from disk directly, and risks introducing serialization artifacts.
2. **IPC is slower than direct disk access:** Agent reads a file in microseconds. Routing through JSON-RPC → Notesage → serialize → JSON-RPC response is orders of magnitude slower.
3. **Watcher already covers follow-along:** The filesystem watcher (500ms debounce, content comparison, auto-reload) handles the "editor updates when agent edits files" case well enough. Adding a parallel write-through-IPC path creates two codepaths for the same thing.
4. **Uncertain agent adoption:** Whether Claude Code, Codex, Copilot, or Gemini actually delegate file I/O to the client (vs using their own tools) is unconfirmed. The capability advertisement may go unused.
5. **Dirty content serving is a footgun:** The only unique benefit — serving unsaved editor content — is a niche edge case that could confuse agents (they'd see content that doesn't exist on disk).
