## 2026-04-23 — plan-tasks + implement-tasks — Phase 1 task plan diverged from PRD success criteria

**The miss.** Phase 1 of `2026-04-21-ui-refresh.md` planned and shipped 100 tasks across 10 milestones (M1.1–M1.10). I built tasks for "create the new sidebar" / "build the floating command bar" / "render the agent orb" / "wire ARIA on the new components". I did NOT build tasks for "mount the existing Tiptap Editor inside the new shell" or "mount the existing chat surface inside the new shell". Those are quietly assumed by the PRD's success criteria ("All of today's user flows verifiable in the new UI") but never explicitly captured as numbered tasks. The plan was internally consistent — each milestone built what it promised — but missing the cornerstone integration work.

**The corrective action.** When the user re-read the PRD success criteria and flagged the gap, we restructured: the post-Foundation work that I'd filed as a separate `phase2-tasks.md` (8 tasks: editor mount, chat mount, polish, manual QA) was folded back into `phase1-tasks.md` as new milestones M1.11 / M1.12 / M1.13. Phase 1 is now 100/109 (Foundation done; Functionality + Polish + Manual QA remaining). The PRD success criteria were rewritten with explicit functional-vs-foundation split + checkboxes marked for what's actually done. `phase2-tasks.md` was deleted. Phase 2 (release semantics) reverts to the PRD's roadmap section.

**Two skill-level lessons.**

1. **plan-tasks must cross-check PRD success criteria, not just the design spec.** At the end of `/plan-tasks`, before sign-off, walk every PRD success criterion and confirm it maps to one or more numbered tasks. If a criterion isn't covered (e.g., "the editor opens markdown files" in a UI-refresh PRD), add tasks before declaring the plan complete. A small "Success criterion → covering task #(s)" table at the bottom of every task breakdown would make planning gaps visible at sign-off — empty cells = gap. Should become a hard step in the SKILL.md.

2. **implement-tasks "Phase done" claim must include a shippability check, not just test-gate green.** All gates passing ≠ the app is usable. Before claiming a phase / release-bundle is closed, do a final "open the actual app and try the user-facing scenarios" pass — even a 5-minute smoke test against the user stories from the PRD. Test gates verify code correctness, not feature correctness. If you can't run the app yourself, explicitly hand the smoke test to the user before declaring done.

**Adjacent observation: Phase numbering and rollout semantics.** The original PRD called the staged rollout "Phase 1 / 2 / 3" (Preview / Default-on / Legacy-removed). When I created `phase2-tasks.md` for the Foundation-finishing work, I conflated "Phase 2 of the implementation" with "Phase 2 of the rollout" — those are different things. The user's mental model was: Phase 1 is a ship-able preview release, Phase 2 is the next *release* (default-on), Phase 3 is the *third* release (legacy gone). My implementation breakdown should have stayed inside Phase 1 (as more milestones) until the preview was ship-able. Lesson: when a PRD already has a phase numbering scheme tied to release semantics, the implementation breakdown should not invent its own competing phase numbers — extend the existing milestones inside the current PRD phase.

## 2026-06-12 — implement-tasks — parent-side worktree git ops ran in the wrong checkout twice (cwd drift)

**The miss.** Twice in one session the orchestrator's "commit in worktree, then cherry-pick/merge into the session branch" sequence ran the second half inside the *worktree* instead of the main checkout, because a `cd <worktree>` (or an earlier `cd src-tauri` for cargo) silently persisted as the shell cwd. Symptoms: a cherry-pick of the worktree's own commit onto itself ("previous cherry-pick is now empty"), and once a `git worktree remove` of the directory the shell was standing in ("Unable to read current working directory"), leaving a dangling branch to recover by hash. A third variant: `ls .claude/worktrees/` appeared to show the MIG worktree *deleted* (relative path resolved from `src-tauri/`), triggering an unnecessary data-loss investigation.

**The fix that worked.** Treat the main checkout path as part of every repo-level git command: `git -C <abs worktree> add/commit` for agent-side ops, then `cd <abs main checkout> && git cherry-pick <hash>` (or `git merge`) for integration — never relying on inherited cwd, never compound `cd X && … && git <integration op>` in one line.

**Skill-level lesson.** implement-tasks step 3's example commands are written relative ("git merge worktree-agent-<id>" from "the main checkout") and assume the orchestrator's shell is already there. In a harness where Bash cwd persists across calls and cargo/pnpm steps cd around, that assumption breaks. The skill should prescribe absolute `-C` forms for both halves: `git -C <worktree> commit …` and `git -C <main-checkout> merge/cherry-pick …`, and explicitly warn against running integration ops while cwd is inside a worktree slated for removal.
